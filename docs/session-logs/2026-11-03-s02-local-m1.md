# s02 — first local session on the M1 (2026-11-03)

Picked up from the s01 cloud session. Local machine: MacBook Air M1, 16 GB, on a metered HSPA+ link (~20 Mbps).

## Setup findings

- **V1 checkout had local-only docs.** `AGENTS.md`, `CLAUDE.md`, `HANDOFF.md`, `ROADMAP.md`, `docs/superpowers/` and `.claude/` were hidden by `.git/info/exclude` (plus `.superpowers/` ignored globally), so they existed only on disk. v2 *tracks* `CLAUDE.md`, `HANDOFF.md` and `ROADMAP.md`, and checkout overwrites ignored files without warning. They were copied to `~/realmgenesis-v1-local-2026-11-03/` (byte-identical, checked with `cmp`) before the switch. Not pushed anywhere: the repo is public.
- All local V1 branches are now on origin (7 had no upstream; `f5-layer-legend` was the only one with commits not on `main`). Local == remote verified per branch.
- `.git/info/exclude` still applies to every branch. Tracked files are unaffected, but a *new* `AGENTS.md` or `docs/superpowers/` on v2 would be invisible to `git status`.
- V1's `node_modules/` (372 MB) shows as untracked on v2; v2's `.gitignore` doesn't cover it. Don't `git add -A`.

## Decision: low-data toolchain

Measured (HEAD Content-Length, rust-lang.org / crates.io):

| piece | MB |
|---|---|
| rustc / rust-std (aarch64) / cargo / clippy / rustfmt | 65 / 27 / 8 / 3 / 1 |
| rust-docs (skipped by the minimal profile) | 22 |
| rust-std wasm32 | 20 |
| all 402 crates in Cargo.lock | 61 (≈24 of it Windows/Linux/web-only) |

- **Chosen:** `rustup set profile minimal`, `rustup toolchain install 1.97.0 -c clippy -c rustfmt`, then `rustup override set 1.97.0` in the repo (a directory override beats `rust-toolchain.toml`, so wasm32 isn't pulled). Crates via `cargo fetch --target aarch64-apple-darwin`, builds with `--offline`. ≈145 MB once.
- **Rejected:** the plain rustup installer (default profile + docs + a second stable toolchain besides the pin, ~250 MB); following the toml as written (+20 MB wasm32, not needed until the web build).
- **Caveat:** the override pins 1.97.0 for this directory. If `rust-toolchain.toml` is bumped, run `rustup override unset` (that also brings wasm32 back via the toml).
- **Flaky-link knobs:** `RUSTUP_DOWNLOAD_TIMEOUT=600`, `RUSTUP_CONCURRENT_DOWNLOADS=1` (both *unstable* in rustup 1.29.2 docs); `CARGO_NET_RETRY=10`, `CARGO_HTTP_TIMEOUT=120`, `CARGO_HTTP_MULTIPLEXING=false`; each step in a 5× retry loop.
- **Disk:** 21 GB free at start (below Matt's 25 GB "soon" line). `target/` for a release build is expected at 2–4 GB (unmeasured; measure after the first build).

## Decision: local resource caps (Matt: builds/tests ≤ half the CPU so the laptop stays usable)

- **v2 sizes its own thread pools** from `std::thread::available_parallelism()` (`rg-tectonics/src/util.rs:112`, `rg-pipeline/src/layers.rs:156`, `rg-app/src/tiles.rs:141`); no rayon. So `cargo -j` / `--test-threads` alone don't cap the engine: every world generation still spawns ~8 threads.
- **CPU: `taskpolicy -b`** (background QoS → E-cores only on Apple Silicon). Measured, n=1 with a download running: 8 pure-compute burners for 6 s used **13.3 CPU-s capped vs 41.0 uncapped** (2.2 vs 6.8 cores). Plus `-j 4` (no point exceeding the 4 E-cores; each rustc is RAM) and `--test-threads=2`. Cost: E-cores are much slower, so build/test wall time goes up (not yet measured).
  - Don't wrap the interactive app (`target/release/realmgenesis`) in it: the UI and tile workers would run on E-cores and misrepresent performance.
  - Rejected: `-j 3 --test-threads=2` alone (the side agent's suggestion), since the engine's own pools ignore both.
- **RAM: no hard cap exists on macOS.** `ulimit -v` fails outright (`setrlimit failed: invalid argument`); no cgroups. The levers are concurrency (`-j`, `--test-threads`), the app's own byte budgets (patch cache 96 MB, channel memo ~140 MB), and measuring peaks with `/usr/bin/time -l`. A soft cap (watchdog that `SIGSTOP`s the cargo process group when `kern.memorystatus_vm_pressure_level` hits warn) is possible but reactive; parked unless measured peaks warrant it.
- **Before each heavy run:** check `top -l 2 -s 2 -o cpu` for After Effects / aerender / Blender actually using CPU (open ≠ busy). At s02 start: AE not running; Blender app not running (only its thumbnailer and MCP helpers, 0%).
- **Disk:** keep every step on the release profile (`cargo test --release`, `cargo clippy --release`); a debug-profile run builds a second dependency tree.
