## Decision: local resource caps (Matt: builds/tests ≤ half the CPU so the laptop stays usable)

- **v2 sizes its own thread pools** from `std::thread::available_parallelism()` (`rg-tectonics/src/util.rs:112`, `rg-pipeline/src/layers.rs:156`, `rg-app/src/tiles.rs:141`); no rayon. So `cargo -j` / `--test-threads` alone don't cap the engine: every world generation still spawns ~8 threads.
- **CPU: `taskpolicy -b`** (background QoS → E-cores only on Apple Silicon). Measured, n=1 with a download running: 8 pure-compute burners for 6 s used **13.3 CPU-s capped vs 41.0 uncapped** (2.2 vs 6.8 cores). Plus `-j 4` (no point exceeding the 4 E-cores; each rustc is RAM) and `--test-threads=2`. Cost: E-cores are much slower, so build/test wall time goes up (not yet measured).
  - Don't wrap the interactive app (`target/release/realmgenesis`) in it: the UI and tile workers would run on E-cores and misrepresent performance.
  - Rejected: `-j 3 --test-threads=2` alone (the side agent's suggestion), since the engine's own pools ignore both.
- **RAM: no hard cap exists on macOS.** `ulimit -v` fails outright (`setrlimit failed: invalid argument`); no cgroups. The levers are concurrency (`-j`, `--test-threads`), the app's own byte budgets (patch cache 96 MB, channel memo ~140 MB), and measuring peaks with `/usr/bin/time -l`. A soft cap (watchdog that `SIGSTOP`s the cargo process group when `kern.memorystatus_vm_pressure_level` hits warn) is possible but reactive; parked unless measured peaks warrant it.
- **Before each heavy run:** check `top -l 2 -s 2 -o cpu` for After Effects / aerender / Blender actually using CPU (open ≠ busy). At s02 start: AE not running; Blender app not running (only its thumbnailer and MCP helpers, 0%).
- **Disk:** keep every step on the release profile (`cargo test --release`, `cargo clippy --release`); a debug-profile run builds a second dependency tree.

## Task: app locks up the M1; dragging is slow (Matt force-quit the app)

Matt: "background rendering is locking up my machine… find the code to optimize, or at least add a red button that says STOP BACKGROUND RENDERING. Also dragging performance is very slow."

**Diagnosis from code (n=0 measurements yet; hypotheses until measured):**
1. **Tile pool takes every core.** `crates/rg-app/src/tiles.rs:141`: `available_parallelism − 1`, clamp 1..8 → **7 workers on the M1**, at normal QoS, each tile 85–240 ms (cloud figure). Up to `workers × 3` = 21 jobs queued; nothing cancels a job whose tile is no longer wanted (after a drag the view moves on, but stale jobs still run to completion).
2. **UI-thread patch builds while dragging.** `app.rs:365–378` calls `terrain.height(dir, 50 m)` (orbit target) and `terrain.height(eye, 30 m)` (clearance) every frame. With the detail network, `TerrainSampler::net_levels` (`rg-terrain/src/lib.rs:115`) builds a whole `net.patch` per 2 km block (`block_m = max(32 × cutoff, 2000)`) on a cache miss. Panning moves the target across blocks almost every frame, so the UI thread builds patches mid-drag, competing with 7 workers. A 30–50 m height is meaningless from orbit.
3. Minor: `ui/mod.rs:390` repaints continuously while the pointer merely hovers the viewport; `describe()` runs per frame on hover.

**Measured (n=1, seed 3, res 320, `bench_tiles`):**

| | P-core (uncapped) | E-core (`taskpolicy -b`) |
|---|---|---|
| patch build, cutoff 40 m (what the UI-thread clearance query pays) | **242 ms** | 924 ms |
| patch build, cutoff 1000 m | 159 ms | 724 ms |
| network tile L4 / L7 / L10 / L12 / L14 | 69 / 56 / 79 / 148 / 60 ms | 353 / 305 / 407 / 761 / 359 ms |
| gully tile (old detail) | 4–13 ms | 20–64 ms |
| world generate (seed 3, Normal) | — | 12.3 s |

- **Correction:** I told Matt to expect 2–3× between P- and E-cores; measured **~4–5×**.
- The two UI-thread queries use different cutoffs (50 m target, 30 m eye) → both `block_m = 2000` but different cache keys (`cutoff.to_bits()`), so a new 2 km block can cost **two** builds, ≈0.5 s of UI thread on a P-core. Panning from orbit crosses blocks almost every frame → the slow drag.
- World generation runs synchronously on the UI thread (`run_deferred` → `rg_pipeline::generate`), using every core for seconds at launch and on G/R. A stop button can't interrupt it (that's the M1b `Job` item).

**Plan (advisor-reviewed, awaiting Matt's go; no code yet, Matt: "don't build or test, plan, prioritise the UI bit"):**
1. **STOP BACKGROUND RENDERING button** (`commands.rs`, `app.rs`, `tiles.rs`, `ui/mod.rs`): `Command::ToggleTileStreaming`; stop = bump epoch + clear in-flight + paused; workers read a shared `Arc<AtomicU64>` epoch and skip stale jobs before `generate` (queue drains in µs; regenerate also stops old-world tiles); paused ⇒ no submits and `streaming` ignores `wanted` (else the 60 fps repaint loop continues); red overlay top-right of the viewport (sidebar can be hidden), label flips to RESUME; pause survives regenerate. Also: repaint on pointer *movement*, not mere hover (`ui/mod.rs:390`).
2. **Drag fix** (`app.rs`): one cutoff for both queries, quantised (powers of two / tile LOD wavelengths: a continuous cutoff misses the cache every zoom frame); `macro_height` when the eye is well above `max_height × exag`. Proper fix later: heights from resident tiles (M1c "tile-height picking").
3. **Worker pool** (`tiles.rs`): half the cores, ≤ 4; utility QoS on macOS (`pthread_set_qos_class_self_np`; `libc` is already in Cargo.lock, offline-safe); skip jobs no longer wanted.

**Implemented (Matt: "you can build now"), all capped builds, clippy clean:**
- `5ed1575` button + epoch cancellation + paused repaint + input-only repaint (+ `settling` flag so the orbit point still eases in after a drag; a current-epoch-only `in_flight.remove`, which fixes a latent double-submit after a cancel).
- `0e2a3ba` `camera_query_cutoff_m`: macro above 10 km clearance; else 2^round(log2(clearance/8)) clamped 32–1024 m. Two unit tests. Not measured in the app yet: expected one ~160–240 ms hitch per block crossing (block ≈ 4× altitude) below 10 km instead of one per frame.
- `f5a5ebe` pool `n/2` clamp 1..4; `QOS_CLASS_UTILITY` on macOS (libc, offline from the lockfile); workers skip unwanted queued tiles and report `None` back.
- Incremental release build of `rg-app` ≈ 4 min capped (mostly the thin-LTO link).
- **Not verified:** Matt hasn't run the new build. Visual/feel check is his next step.
- **Review fix (advisor):** the cut-off was chosen from the eye's clearance, but `EarthCamera::target()` includes `target_height_m`, which the query itself updates. Near the 10 km switch or a power-of-two step the band could flip every frame, `settling` would never clear, and the 60 fps loop would return. Now chosen from `distance_m · cos(tilt)` (height above the orbit point), which the queried height doesn't move. The release binary built before this fix is stale.
- CI green on `7219e48` (test, web, macOS/Windows/Linux), so the wasm32 `if !self.paused` path compiles.

- **New hypothesis (n=0, untested): the tile band-limit.** `tile.rs:60` keeps detail down to 2 cells per wavelength (Nyquist floor), so a network valley is ~2 cells wide and draws as a 2–3-vertex zigzag; with `max_cell_px` 6 that's ~12 px of faceted V. ## B: regional "Gaea mode" design (M0 proposed)

- Research: Haiku + Exa digest (licences per LICENSE file, by the agent; re-verify before porting). Folded into `docs/design/regional-detail.md`.
- Advisor: architecture right (reuse rg-erosion on a regional Grid, macro as boundary, schema-5 chunks as data tiles, render via macro_height override), **but prove the look first: M0 = headless spike PNG + metrics, judged by Matt before any schema/UI work.** Critical physics: a hillslope regime (threshold slope ~33°) or stream power at 150 m makes knife ridges; drained upsampling (not bicubic) or pits → dotted lakes; inflow area injection at edges; same K_eff/m/n. 2048² default; 4096² only after measuring RSS.
- **Verified:** the core solve (`solve_full_with_progress`), `priority_flood_fill_to`, `lakes.rs`, `Network::route` and `diagonal_mask` use only `grid.dir/n/weight/neighbors`, so a regional raster Grid works without solver changes.
- **Matt: "generating at different resolutions also result in very different terrains, even with the same coastlines and biomes."** Cause found: initial roughness (`solver.rs:561`) and Rho8 (`solver.rs:785`) are hashed by **node index**, so each resolution gets a different random field (plus stream power's intrinsic resolution dependence). Coastlines/biomes match because tectonics noise is position-keyed. Fix (position-keyed roughness at a fixed physical wavelength) changes every world and may touch goldens: Matt's call.

- **v1 (refuted as a recipe): rerunning the macro's tectonic uplift at 293 m.** Small catchments can't keep up with uplift, so the whole window rose until the talus cap held it: a central plateau with escarpments, the macro's big shapes moved, an edge frame.
- **v2/v3 (works): Gaea/WM/Terragen-style detail erosion** (no uplift, short carve) plus **low-pass anchoring** (h += 3×box-blur(macro − h) at ~½ macro cell, so everything coarser than a macro cell is the macro's) plus an **edge taper**. The large structure matches the macro; dendritic valleys; seam-free.
- Remaining look issues (full-res crop): a "brushed" texture of short parallel gullies on grid diagonals (D8 bias at the finest level, few steps; partly the macro's NE–SW grain) and faint blocky luminance patches at macro-cell scale (likely the box-blur anchoring). Candidate fixes: position-keyed Rho8 on the regional grid, more fine-level steps, hillslope diffusion, a Gaussian (not box) anchor, and checking the drained upsampling.
- PNGs (outside the repo): `~/RealmGenesis/spike/s1-*.png` (+ `_macro.png` for the same window from the smooth macro).
- **Matt's verdict on v3:** "more or less a 'dumb' upscale… the broad strokes of the relatively straight base rivers and valleys… have added detail, but not naturalistic flows and curves… Squinting at either sample, I can still see a griddy pattern… This is the right direction for Gaea mode, but… the 'broad strokes' still lend to a more mechanistic terrain."
- **Refuted: "anchoring at ~1 macro cell gives a natural upscale".** It reproduces the macro's planform exactly, and the macro is routed in 8 directions on a 10 km grid (straight runs, 45° turns), so the window can only add texture. Part of the griddiness is upstream (the macro); fixing that is a global change (parked next to the resolution-coherence item).
- Advisor plan: one lever per run, same window, same crop: (1) anchor to the bicubic macro (blocky patches?), (2) position-keyed node jitter ±0.3 cell with regional Rho8 off (brushed diagonals), (3) anchor at 3–5 macro cells with a longer level 0 (trunks reroute), (4) domain warp only if trunks stay straight, faded at coast, window edges and river crossings. Add a griddiness number: the 8-fold aspect component |Σ w·e^{i8θ}| / Σ w (w = gradient magnitude). Stream power gives dendritic networks, not meanders; warp is the only cheap route to sinuosity (an effect, not physics).
- Design consequence for M1/M2 (decide before M1): once a window reroutes valleys, it must commit its own rivers/lakes and suppress the macro overlay inside, keeping the edge crossings; jittered nodes need resampling to regular data tiles.

- **Matt's question: "What if we let go of the grid mesh for geometry and generation, and just use raster displacement maps?
